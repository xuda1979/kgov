1 引言
============================================================

1.1 编写目的
    本说明书描述《Kafka-Govern（kgov）V1.0》的总体设计与详细设计，
    说明系统结构、模块划分、接口约定、数据结构及关键算法流程，供
    软件维护、二次开发及验收评审人员阅读。

1.2 系统背景
    Kafka-Govern 是为中小企业信息团队开发的 Kafka 主题治理助手，
    面向“Kafka + Schema Registry”环境提供轻量、可离线运行、可接入
    CI 流水线的治理能力，覆盖“模式演进治理—数据质量治理—治理报告”
    全流程。系统自托管、离线优先：全部核心功能基于 JSON / YAML
    数据包运行，不依赖任何云服务；可通过可选组件连接真实 Kafka
    集群与 Schema Registry。本软件由开发者许达（中国移动研究院）
    独立设计、编码与测试完成，源代码量约 7860 行（不含注释与空行，
    含测试代码），详细模块行数统计见《用户手册》附录。

1.3 术语定义
    - topic（主题）：Kafka 中消息的逻辑归类单元。
    - Schema：消息的结构化定义，本系统支持 Avro 与 JSON Schema 两种体系。
    - Compatibility（兼容性）：Schema 演进前后是否可互读，分为
      Breaking（破坏性）、Non-Breaking（非破坏性）、Additive（新增兼容）
      三级。
    - Confluent Wire 格式：Confluent 生态约定的消息序列化帧，
      为 0x00 魔数 + 4 字节大端 Schema ID + Avro 二进制负载，
      头部固定 5 字节。
    - DSL：领域特定语言，此处指数据质量规则的声明式描述格式。
    - 脏数据：不符合既定约束（类型、必填、枚举、正则、范围、非空）的消息。
    - 陈旧度（stale）：主题超过阈值时间未有消费或消息写入的状态。

2 总体设计
============================================================

2.1 系统结构
    系统为单进程命令行应用，入口为 kgov.cli.main()。采用“命令派发 +
    功能模块”的分层结构：

    kgov.cli            CLI 参数解析、子命令派发、退出码与错误处理
        |
        +--- kgov.schema_diff     Schema 兼容性比较引擎
        +--- kgov.rules           脏数据规则 DSL 解析与消息校验
        +--- kgov.report          治理报告汇总与导出
        +--- kgov.registry        Schema Registry 客户端（REST）
        +--- kgov.mock_registry   本地只读 MockRegistry（HTTP 服务）
        +--- kgov.broker          真实 Kafka 对接层（可选依赖）
        +--- kgov.model           公共数据模型
        +--- kgov.rules_errors    规则解析异常类型

    依赖方向自顶向下：cli 仅调用各功能模块对外函数，功能模块之间
    不相互依赖（broker 模块可能使用 registry 的客户端类型做入参）。

2.2 模块划分及职责

    模块                职责
    -----------------  -----------------------------------------------
    model              兼容性枚举、差分结果与报告的数据类、通用工具函数
    schema_diff        两个 Avro / JSON Schema 的逐字段对比与兼容性判定
    rules              规则 DSL（YAML/JSON）加载、字段校验、违规报告
    report             主题治理状态汇总（owner/陈旧度/违规计数）与导出
    registry           Schema Registry REST 客户端（subjects/versions/ids）
    mock_registry      本地只读 HTTP 服务，模拟 Confluent 注册表端点
    broker             AdminClient 元数据、消费组描述、主题消息读取、
                      Confluent Wire Avro 解码（可选 confluent-kafka）
    cli                六个子命令：schema-diff / check / report /
                      registry / topics / export，统一退出码约定

2.3 接口设计

2.3.1 内部函数接口
    - schema_diff.diff_schemas(before: dict, after: dict) -> SchemaDiffReport
      输入两个已解析的 Schema 字典（跨格式禁止比较），输出差分报告，
      报告含 compatibility（Breaking/Non-Breaking/Additive）、
      results（逐项差分明细）与结构化 to_dict / to_markdown 输出。
    - rules.build_ruleset(spec: dict) -> RuleSet
      rules.validate_message(ruleset, message) -> list[Violation]
      rules.validate_fixture_file(config, messages_json, ...) -> 汇总结果
    - report.build_governance_report(topics, registry, groups, rules,
      messages, violations) -> GovernanceReport
    - registry.SchemaRegistryClient(base_url, token, timeout)：
      提供 get_subjects / get_versions / get_version / get_schema_by_id /
      get_config / to_fixture_dict 等方法。
    - broker.list_topics(bootstrap) / consumer_groups(bootstrap) /
      read_topic(bootstrap, topic, n, timeout)：
      拉取主题元数据、消费组、在线消息（需 confluent-kafka）。
    - broker.AvroRecordDecoder(client)：
      可调用对象，负责把 Confluent Wire 字节帧解码为字典。

2.3.2 外部接口（Schema Registry REST，Confluent Wire 协议）
    客户端遵循 Confluent Schema Registry HTTP API 约定：
    - GET /subjects                      列出全部 subject；
    - GET /subjects/{subject}/versions   列出版本号；
    - GET /subjects/{subject}/versions/{version|latest}
                                        取指定版本 Schema（含兼容级别）；
    - GET /schemas/ids/{id}              按 Schema ID 取 Schema 定义；
    - GET /config/{subject}              取 subject 级别的兼容策略。
    响应中的 schema 字段可能为 JSON 字符串，客户端通过
    _parse_schema_string 将其规范化为对象。

2.3.3 外部接口（Kafka）
    - AdminClient.list_topics() 获取主题名、分区数、副本因子；
    - consumer_groups/list_consumer_groups + describe_consumer_groups
      获取消费组状态与成员、最近消费时间；
    - 消息读取使用 Consumer，group.id 取进程唯一串
      （f"{group_id}-{id(object()):x}"），enable.auto.commit=False，
      auto.offset.reset=earliest，读取达到 n 条或超时后停止。

2.4 数据结构与存储设计
    系统不依赖外部数据库。全部持久数据为 JSON / YAML 文件：

    - topics.json      {"topics": [{"name", "partitions",
      "replication_factor", "owner", "tags[]", "schema_subject",
      "latest_message_at"}]}
    - registry.json    {"subjects": {"<subject>": [{"id", "version",
      "compatibility", "schema"}, ...]}}
    - consumer_groups.json  {"groups": {"<topic>": {"topic", "group",
      "last_consumed_at", "consumer_count"}}}
    - rules.yaml       DSL 规则文件：version / topic / name / rules（或
      fields）字段约束说明。
    - messages.json    消息样本：{"topic", "partition", "messages":
      [{"offset", "key", "value"}]}，或裸数组。

    输出文件：markdown 升级指引（.md）、兼容性矩阵 / 治理报告（.json）、
    报表（.csv）、违规明细（.json）。

2.5 全局判定与输出约定
    所有命令共用四级退出码约定（本项目创立的社区级 CI 门禁约定）：
    - 0：通过（无违规 / 兼容 / 输出成功）；
    - 1：门禁失败（发现违规、超出门禁阈值、Breaking 差分）；
    - 2：用法 / 配置错误（argparse 校验失败）；
    - 3：运行时错误（文件缺失、解析失败、连接失败）。

3 详细设计
============================================================

3.1 schema_diff 模块（Schema 演进兼容性检测）

3.1.1 数据结构
    - DiffResult：冻结数据类，记录 path、format、kind、message、before、
      after 等差分明细项；
    - SchemaDiffReport：整体差分报告，字段含 subject、format、before_
      version、after_version、kind（两大体系统一为 Breaking /
      Non-Breaking / Additive）、results、notes；
        to_dict() 追加 "compatible" = (kind != Breaking) 并统一 JSON 序列化；
        to_markdown() 输出“# Schema diff”标题、格式/版本/兼容性头与
        变更清单（- 删除 / ~ 修改 / + 新增）。

3.1.2 算法
    parse_schema：按“字段带 type 或含 $schema/properties”自动识别
    Avro / JSON Schema 两种格式。

    _avro_diff（Avro 逐项比较）：
    - 联合类型 union：比较分支集合；新增分支判定 Additive，移除分支
      判定 Breaking；
    - 基础类型：按优先级表 _PRIMITIVE_PRIORITY（null=0、boolean=1、
      int=2、long=3、float=4、double=5、bytes=6、string=7）判断：目标
      优先级高于源为基础类型放宽（Non-Breaking），低于源为基础类型
      收紧（Breaking）；（双向，即 int→long 不破、long→int 破）；
    - record 字段：删除字段判定 Breaking；新增字段若带默认值或类型
      含 null（可选）判定 Additive，否则判定 Breaking；
    - enum：仅移除符号判定 Breaking，仅新增符号判定 Additive；
    - array/map：递归比较 items / values 类型；fixed：比较 size。

    _js_diff（JSON Schema 逐项比较）：
    - type 收窄判定 Breaking，放宽判定 Non-Breaking
      （配 _types_assignable_set / _js_strings_assignable，
      number 兼容 integer 等）；
    - required 数组新增必填字段判定 Breaking；
    - properties 移除字段判定 Breaking，新增可选字段判定 Additive；
    - additionalProperties 由允许改为禁止判定 Breaking；
    - enum 移除取值判定 Breaking；
    - 界约束：minLength/minItems/minimum 提升、maxLength/maxItems/
      maximum 降低，均判定 Breaking（约束收紧）。

    classify：任一明细为 Breaking → 整体 Breaking；否则任一明细为
    Additive → 整体 Additive；否则为 Non-Breaking。

3.2 rules 模块（脏数据规则扫描）

3.2.1 数据结构
    - FieldCheck：单字段检查项，含 name、type、required、enum、pattern
      （并预编译正则 compiled_pattern）、range（minimum/maximum）、
      non_null；
    - RuleSet：version、topic（默认为 "*" 全主题）、name、fields；
    - Violation：违规记录（rule、topic、partition、offset、key、field、
      check、message），to_dict 用于 JSON 输出；
    - Message：topic、partition、offset、key、value。

3.2.2 校验算法 validate_message
    对每条消息按顺序执行字段检查链，逐条累积 Violation：
    1. 主题匹配：ruleset.topic == "*" 或与消息 topic 相等，否则跳过；
    2. required：字段缺失即违规；
    3. non_null：字段值存在但为 None 即违规；
    4. type：值类型须在允许集合内（_type_ok 中 integer 与 int 等价，
       number 接受 int/float，布尔值不归入 int）；
    5. enum：值须属于枚举集合；
    6. pattern：值须匹配预编译正则；
    7. range：数值须落入 [minimum, maximum]。
    任一检查失败即记录一条 Violation，并继续检查其余字段，保证一次
    扫描输出全部违规项。

3.2.3 门禁逻辑
    check 子命令要求必须提供数据源（--messages 或 --broker --topic），
    否则按运行时错误（退出码 3）拒绝空扫描，避免 CI 门禁静默通过；
    gate_failed = 存在违规 且 (max_violations<=0 或 违规数>max_violations)，
    超门禁退出码 1。

3.3 report 模块（治理报告）

3.3.1 数据结构
    - StalenessSettings：consumer_grace_seconds 默认 3 天（86400*3）、
      producer_grace_seconds 默认 2 天（86400*2）、no_consumer_
      since_epoch 标志；
    - TopicState：name、owner（默认 unknown）、tags、partitions、
      replication_factor、schema_subject、schema_version、schema_state、
      latest_message_at、last_consumed_at、stale、violation_count。

3.3.2 陈旧度判定算法
    1. 主题有消费组：统计最近 last_consumed_at，距今超过
       consumer_grace_seconds（3 天）判定 stale；
    2. 主题无消费组：按生产者规则，latest_message_at 距今超过
       producer_grace_seconds（2 天）判定 stale；
    3. 无消费组且无最近消息（epoch 起点）置 no_consumer_since_epoch。

3.3.3 输出
    report_to_csv 输出固定列：name, owner, tags, partitions,
    replication_factor, schema_subject, schema_version, schema_state,
    latest_message_at, last_consumed_at, stale, violation_count；
    GovernanceReport.to_json 输出 JSON；支持 -o 指定位与 .csv 后缀
    自动切换格式。

3.4 registry 模块（Schema Registry 客户端）
    SchemaRegistryClient 基于 urllib 实现，构造参数为 base_url、（可选）
    token、timeout（默认 10 秒）。请求路径经 _quote_path 转义防注入；
    方法：
    - is_reachable()：探测 /subjects 有效性；
    - subjects() / versions(subject)；
    - get_version(subject, version)：版本列表取最后一版为 latest，
      版本详情合并 /config 返回的兼容策略；
    - get_schema_by_id(schema_id)；
    - to_fixture_dict()：导出为 {"subjects": {...}} 离线 fixture 形态。

3.5 mock_registry 模块（本地只读 MockRegistry）
    RegistryHandler 继承 BaseHTTPRequestHandler，do_GET 路由：
    /subjects、/subjects/{subject}/versions、/schemas/ids/{id}、
    /config/{subject}、/mode；do_POST 统一返回 404（只读）。数据源为
    fixture 字典，支持 add_subject 动态注入（供测试制造 Schema ID）。
    MockRegistry.start() 默认绑定 127.0.0.1 临时端口，通过 context
    manager 自动启停；对外暴露 base_url 与 client 属性，使 kgov
    registry 命令与集成测试能够完成真实 HTTP 往返。

3.6 broker 模块（真实 Broker 可选对接）

3.6.1 消息解码链 _decode_value
    按 JSON → Confluent Wire Avro → 文本/十六进制 的顺序自适应解码，
    保证任何载荷都不会中断扫描：
    1. 尝试 UTF-8 JSON 解析成功即返回对象；
    2. 否则若提供 AvroRecordDecoder，判断字节帧长度 > 5 且首字节为
       0x00，则解析 4 字节大端 Schema ID 并从注册表取 Schema 解码；
       任何失败返回 _UNDECODED 哨兵；
    3. 解码器拒绝时回退为 UTF-8 文本；二进制不可解码时输出
       {"$bytes": "hex"} 形式，不丢失原始字节信息。

    AvroRecordDecoder 内部带 Schema ID 缓存（dict），仅接受 type 为
    record 的 Schema，底层用 avro.io.DatumReader + BinaryDecoder。

3.6.2 依赖门禁
    _require_kafka() 在 confluent-kafka 缺失时抛出 NeedsBrokerError
    （ImportError 子类），引导用户执行 pip install "kgov[broker]"，使
    离线核心功能不受可选依赖影响。

3.7 cli 模块（命令调度与统一退出码）
    main() 解析参数后按 subcommand 派发；捕获 SystemExit（argparse
    失败退出码 2）、CliError（打印错误到 stderr 后退出码 3）、
    KeyboardInterrupt（130）、BrokenPipeError（0）。_write_out 负责
    统一输出：指定 -o 写文件（路径不存在则创建），否则打印到 stdout；
    --force 与无路径场景冲突时报错。六个子命令参数与功能：
    - schema-diff --before/--after/--format/--subject/--json/-o；
      输出 Markdown 或 JSON，Breaking 返回退出码 1；
    - check --config/--messages/--broker/--topic/
      --max-violations/-o/--quiet；门禁失败退出码 1；
    - registry --registry-url/--subject/-o；
    - topics --bootstrap/-o；
    - report --topics/--registry/--groups/--rules/--messages/
      --violations/--format/-o；
    - export --type/--format，翻译为对应子命令参数后复用其实现。

3.8 关键流程示例

    schema-diff 主流程：
        main → cmd_schema_diff
            → 解析 before/after 来源（本地文件 / http(s) URL /
              简写 host:port/subject/version）
            → diff_schemas(before, after)
            → 按 --json 或扩展名选择序列化
            → Breaking 时返回退出码 1，否则 0

    check 主流程：
        main → cmd_check
            → 校验规则文件存在、数据源非空（缺一即退出码 3）
            → load_rules_file / build_ruleset
            → 数据源分派（--messages 读 JSON fixture，--broker 走
              broker.read_topic 并对 wire 帧解码）
            → 逐条 validate_message 累积违规
            → 输出违规样本（主题/分区/偏移量/键/字段/失败项）
            → 门禁判定返回退出码 0 或 1
